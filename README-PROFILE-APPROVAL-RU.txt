ZELPX — исправление обновления профиля подрядчика
=================================================

Что обнаружено в исходном ZIP
-----------------------------
1. В contractor.html функция saveCompany() напрямую обновляла profiles и contractors.
   Поэтому имя, телефон, название бизнеса, контактный email, адрес и часть настроек
   менялись в активной записи до одобрения администратора.
2. При одобрении функция Supabase использовала COALESCE для значений из заявки.
   Если подрядчик очищал поле, старое значение могло остаться в активной записи.
3. Триггер trg_zelpx_attach_signup_service_categories добавлял категории услуг
   непосредственно в активную таблицу при создании подрядчика, обходя очередь проверки.
4. В отправке профессий часть данных лицензии формировалась в браузере, но затем
   отбрасывалась перед вызовом RPC. Это могло мешать одобрению профессий с лицензией.

Правила после установки
-----------------------
- Только service_radius_miles подрядчик меняет напрямую; диапазон 1–250 миль.
- Имя, телефон, фото профиля, название бизнеса, контактный email, адрес, ZIP,
  координаты, лицензия, страховые данные и уведомления отправляются на одобрение.
- Выбранные услуги/профессии и категории не становятся активными до одобрения.
- При одобрении активные данные заменяются. Значение null/пустое очищает старое поле; название компании обязательно и не может быть пустым.
- При отказе действующий профиль и услуги остаются без изменений.
- Предыдущая и новая версии сохраняются в contractor_profile_history.
- Просмотренные заявки остаются в contractor_change_requests; удаление истории
  подрядчиком и администратором отключено.
- ID подрядчика не меняется; заявки, покупки, кошелёк, переписки и сообщения
  сохраняют существующие связи.

Email
----
Изменение contractors.email означает контактный email компании. Email для входа
в Supabase Auth этим процессом не меняется: для него требуется отдельная процедура
смены email с подтверждением нового адреса.

Порядок установки (важно)
------------------------
1. Сначала сделайте свежую резервную копию проекта Supabase и убедитесь, что она
   доступна для восстановления.
2. Сначала проверьте миграцию на отдельной тестовой базе/ветке. Не запускайте её в production
   вручную до проверки и отдельного подтверждения. Старый supabase-contractor-profile-save-delete.sql
   из исходного ZIP не выполняйте.
3. Убедитесь, что SQL выполнился без ошибок. Затем проверьте в Supabase:
   - таблицу contractor_profile_history;
   - функции submit_contractor_change_request и review_contractor_change_request;
   - триггеры защиты profiles и contractors;
   - что signup-триггер прямой записи категорий удалён.
4. После успешной проверки и отдельного подтверждения примените миграцию к production,
   затем загрузите файлы ZIP в GitHub/Vercel.
5. Проверьте тестовым подрядчиком: отправка изменений, радиус, изменение услуг,
   одобрение, отказ, очистка старого значения и запись истории.

Статус этой сборки
------------------
Это подготовленная сборка для проверки. SQL-миграция подготовлена, но не применена
к рабочей базе; Vercel/GitHub не изменялись. Не считайте сайт обновлённым, пока
миграция и новая версия портала не установлены и не проверены.
