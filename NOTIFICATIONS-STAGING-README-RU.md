# ZELPX — изолированная проверка push-уведомлений

## Что подготовлено
- `supabase-notifications-staging.sql` — минимальная тестовая схема для маршрутизации push-событий.
- `supabase-notifications-staging-hardening.sql` — атомарный claim outbox, повторные попытки, индексы и явные server-only RLS policies.
- `supabase-functions/dispatch-push-notification/index.ts` — серверный отправитель push; принимает webhook только с отдельным секретом.
- Изменения предназначены для отдельного Supabase-проекта `zelpx-portal`. Production `zelpx-database` не менялся.

## Логика безопасности
1. Push о новом лиде ставится в outbox только для подрядчиков со статусом `verified`, чей ZIP совпадает, чьи координаты попадают в радиус обслуживания или у кого совпадают город и штат при отсутствии координат.
2. Push о сообщении всегда содержит общий текст «You have a new message...». Текст переписки не записывается в outbox и не попадает в payload.
3. События дедуплицируются по типу, исходной записи и получателю.
4. Обработка outbox атомарно блокирует событие на пять минут, чтобы повторные webhooks не отправляли одинаковое уведомление параллельно.
5. Таблицы закрыты от ролей `anon` и `authenticated`; доступ оставлен серверной роли. Пользовательские политики/экран настроек подписки требуют отдельного интеграционного этапа.

## Что уже проверено в staging
- Тестовые записи полностью синтетические.
- Из четырёх тестовых подрядчиков push о лиде получили два: verified + совпадение ZIP или радиуса.
- Verified подрядчик вне радиуса не получил событие.
- Pending подрядчик с совпадающим ZIP не получил событие.
- Сообщение от клиента маршрутизировалось подрядчику, а сообщение от подрядчика — клиенту.
- В outbox не оказалось текста ни одного тестового сообщения.
- Ни один реальный push не отправлялся.

## Почему фактическая отправка пока выключена
В Supabase-проекте `zelpx-portal` ещё не настроены отдельные staging VAPID-ключи и `ZELPX_PUSH_WEBHOOK_SECRET`. Production secrets намеренно не копировались. Edge Function пока добавлена в GitHub, но не развёрнута в Supabase; это исключает случайную отправку уведомлений реальным пользователям.

Перед включением доставки нужно:
1. Сгенерировать отдельную VAPID-пару для staging.
2. Добавить в Edge Function Secrets staging-проекта: `ZELPX_PUSH_WEBHOOK_SECRET` (случайное значение минимум 32 символа), `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`.
3. Развернуть функцию `dispatch-push-notification` с `verify_jwt=false`; она сама проверяет заголовок `x-zelpx-push-secret`.
4. Настроить Database Webhook на INSERT в `public.push_notification_outbox`, направив его в эту функцию и передав отдельный staging secret в заголовке.
5. Подключить staging frontend к staging URL и publishable key, создать тестовые аккаунты и подписки.
6. Проверить доставку на тестовых устройствах и отказ доступа между аккаунтами. Только после этого рассматривать Preview deployment.

Не добавляйте VAPID или webhook secrets в GitHub, SQL-файлы, frontend или переписку.

## Ограничения
Это тестовый каркас уведомлений, а не полная копия Production-схемы. Он не включает Stripe, оплату, покупку лидов, реальные аккаунты, регистрацию или клиентский UI. Никаких изменений в Production и Vercel не выполнялось.
